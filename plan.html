01 / OVERVIEW

文档概述

本方案采用 React＋Hono＋Deep Agents（LangChain／LangGraph）＋PostgreSQL＋Redis。Agent 运行在独立 Worker 中；官网、商户后台与管理员后台共用独立前端工程，Hono 提供 REST API，BullMQ 负责排队与并发控制，Langfuse 记录完整运行链路，全部组件通过 Docker Compose 统一部署。

首期功能范围

  1. 商户注册、登录、输入邀请码获得可用权益。
  2. 一键创建客服，进入聊天式配置；可上传多文件。
  3. 配置 Agent 按优先级补齐信息，生成并校验客服 Skill，达到最低条件后自动置为“可用”。
  4. 商户创建 API Key，通过客服 ID＋Key 调用非流式 /chat。
  5. 运行时 Agent 只读当前 Skill，通过 response 回复，通过 ask_human 请求人工。
  6. 商户可测试、查看求助、选择建议回复或接管会话；Langfuse 可还原完整运行链路。
  7. 管理员统一管理商户、客服、邀请码和平台 LLM Provider／模型，关键操作保留审计记录。
  8. 应用、PostgreSQL、Redis、文件存储与 Langfuse 通过 Docker Compose 一键启动，并使用命名卷持久化。

非首期范围

在线支付OCR向量数据库团队 RBACShell／代码执行商户自带模型 Key原始思维链嵌入式聊天插件

文档中的时间上限、目录与字段为设计默认值，可在评审后调整。本轮交付内容为技术设计与实现计划，不包含产品 MVP 代码或可安装的 Skill 包。

Deep Agents 官方生产指南不建议在 Web 服务中直接使用宿主 FilesystemBackend。[官方资料 3] 本方案让模型只看到每客服独立的虚拟根目录；物理路径由服务端解析，禁止 ..、绝对路径和跨客服访问。首期可在隔离 Worker 容器中挂载仅含业务文件的持久卷，不提供 Shell。

“创建 AI 客服”操作不设置额外表单。服务端创建默认名称、配置线程和草稿 Skill 后跳转至配置页，客服名称可在后续配置过程中修改。

  1. 注册并登录。密码使用 Argon2id 哈希，会话写入 HttpOnly Cookie；首期无需邮箱验证。
  2. 邀请码激活。事务内校验有效期、剩余次数和商户是否已激活，写购买记录与权益；不涉及支付。
  3. 一键创建。写入客服记录、配置线程、草稿 Skill v1，初始状态为 configuring。
  4. 进入配置。页面展示固定上传提示与 Agent 首条引导，不要求先填表。
  1. 接收输入。文本进入配置会话；文件先落原始目录，再异步生成文本副本和解析报告。
  2. 配置 Agent 分析差距。固定加载 create-customer-service，读取已有草稿、聊天和行业提问参考。
  3. 每轮只问最重要的 1–2 个问题。优先身份、业务对象、服务范围与边界，避免问卷式轰炸。
  4. 更新草稿。把已确认信息写入 role、business_context、rules 和对应 references；未知项明确标记，不编造。
  5. 确定性校验并发布。最低条件满足后生成不可变 Skill 版本，原子切换 active 指针，客服状态改为 ready；之后仍可继续补充。
  1. 外部调用。调用方以客服 ID＋API Key 提交新消息和客户端生成的 request_id。
  2. 排队与执行。原 /chat 请求保持等待；调用方可用同一 request_id 查询 queued／running 等状态。
  3. 完整 JSON 返回。正常回复、等待人工、被新消息取代或失败均为明确 JSON，不推送 Token 流。
  4. 人工介入。ask_human 创建求助并暂停 AI；商户在后台选择建议回复或接管。
  5. 恢复。建议回复发送后可恢复 AI；接管期间由人工回复，直到商户点击“交还 AI”。

用户与客服管理规则

  • 停用商户后，该商户的登录会话失效，其全部客服停止接受新 Run；已有数据与文件保留。
  • 管理员强制停用客服时，运行中的 Run 按当前状态完成或安全取消，新请求返回 409 service_disabled。
  • 删除商户或客服采用软删除，默认不物理删除消息、Skill 与审计记录；物理清理由单独的保留策略执行。
  • 管理员默认查看配置摘要、状态和用量，不默认展示商户文件正文及终端用户会话内容。
  • 所有状态修改、密码重置、Key 吊销和模型配置变更写入管理员审计日志。

LLM Provider 与模型配置

平台级模型配置项
对象配置字段处理规则
llm_providers名称、类型、base_url、api_key、组织／项目等提供商参数、启用状态支持 OpenAI 兼容、Anthropic、Gemini；API Key 加密入库，接口仅返回掩码
llm_modelsprovider_id、模型 ID、显示名、上下文上限、工具调用、视觉、JSON、推理摘要能力模型 ID 支持手工录入；提供商支持时再自动发现，能力由管理员确认并用于运行时校验
model_assignments场景、model_id、优先级、启用状态分别设置配置 Agent 与运行时 Agent 的平台默认模型，可选按客服覆盖
连接测试Provider、模型 ID、测试类型先校验凭据与网络，再执行最小工具调用请求；不支持模型列表接口时仍允许手工配置

模型解析顺序为“客服场景覆盖配置 → 平台场景默认配置 → 返回明确的未配置错误”。配置 Agent 与运行时 Agent 可分别使用不同模型。每个 Run 记录实际使用的 model_id、Provider 配置版本和模型能力快照，便于复现与审计。

LLM 密钥保护要求

API Key 使用 AES-256-GCM 加密存储，主密钥通过 MODEL_CONFIG_ENCRYPTION_KEY 环境变量注入。只有 API 的测试连接逻辑和 Worker 的模型工厂可在服务端解密；浏览器、商户接口、Langfuse metadata 与普通日志均不得包含明文。

# Create Customer Service

## 目标
把商户输入与文件整理成可运行、可追溯、不过度承诺的客服 Skill。
所有事实必须来自商户明确输入或上传资料；不知道就标记 unknown。

## 每次执行
1. 读取当前草稿 SKILL.md、数据库中的 readiness 状态和本次新增消息／文件索引。
2. 判断公司与产品类别，只读取最相关的一份 industry-*.md。
3. 合并已有事实，生成缺口列表；不要重复询问已经回答或被跳过的项。
4. 按 P0 → P1 → P2 排序，每轮最多问 1–2 个相关问题。
5. 将确认信息写入 role、business_context、rules 或合适的 references。
6. 运行校验；满足 P0 可用条件时发布新版本，否则输出下一个最重要的问题。

## 采访约束
- 先利用文件和聊天答案，再提问；不要把资料阅读变成商户的作业。
- 优先开放式问题，再给简短示例；一次不要跨多个主题。
- 用户拒绝、不知道或暂不回答时，记录 unknown／deferred 并继续。
- 不因追求“完整”而阻塞可用状态；缺少事实时使用保守回复与人工兜底。
- 高风险行业只补充边界问题，不生成诊断、承诺收益等专业规则。

## 发布条件
SKILL.md 结构有效、索引目标存在、P0 检查通过、references 非空且有来源。
发布由服务端事务完成；Agent 不直接修改 active 指针。

配置项优先级与就绪条件

用缺口驱动提问，而不是固定长问卷
优先级需要知道什么缺失时怎么处理是否阻塞可用
P0 必须客服身份、公司／业务对象、主要产品或服务、负责范围、未知问题的人工兜底先问最重要的 1–2 项；至少要知道“为谁、围绕什么业务服务”是，但可使用明确的安全兜底
P1 重要常见问题、价格／交付／售后政策、服务时间、联系方式、明确禁止事项P0 后问；未回答就标记未知，回复时不得猜测否
P2 增强语气、示例对话、品牌词、复杂产品细节、促销与增值规则后台持续补充，不主动拉长首次配置否
最低就绪条件

客服身份与业务对象不能完全为空；服务范围未知时默认“仅根据已有资料回答，其他问题转人工”；事实缺失时默认“不知道并升级”，而不是继续追问商户。通过校验后立即发布 v1 并置为可用。P1／P2 后续每轮更新都可生成新版本，但旧版本保持在线直到新版本校验通过。

行业参考文档的使用方式

行业文档只负责提醒 Agent 还应该了解什么，不提供某家商户的事实，也不直接成为运行时客服的答案。配置 Agent 判断类别后只读最相关的一份；跨行业时可再读第二份，避免全部装入上下文。

电商零售：订单、商品、履约与售后

追问商品／订单信息来源、库存与价格是否会变化、发货范围、物流时效、退换条件、优惠叠加、发票和售后升级。若没有订单工具，运行时必须明确“无法查询实时订单”，不能假装已查询。

软件／SaaS：账号、订阅、功能与故障

追问产品版本、套餐差异、账号与权限、试用／续费／退款、数据导入导出、支持渠道、故障升级和服务时间。区分公开产品知识与需要登录后才能查询的租户数据。

教育培训：课程、报名、学习与退费

追问课程对象、开课形式、时间表、报名门槛、价格、试听、退费、证书与学习平台问题；不得承诺录取、就业或考试结果。

本地服务／旅游：预约、门店、改取消与库存

追问服务区域、门店／地址、可预约时间、价格单位、取消改期、到场规则、突发关闭与人工联系方式。没有实时库存工具时不得确认可预约。

B2B／制造：规格、报价、交期与定制

追问产品规格来源、最小起订量、报价有效期、交期、定制能力、样品、验收、质保与技术支持。引导客服收集线索，而不是自行承诺最终报价。

医疗健康／金融保险：只强化安全边界

追问合法服务范围、人工资质、隐私与紧急升级流程。默认不做诊断、处方、投资建议或收益承诺；紧急情况应给出人工或当地紧急渠道指引。首期若无法验证合规要求，建议限制此类商户上线。

06 / RUNTIME DESIGN

运行时 Agent 设计

每次生产 Run 都从数据库读取当前会话消息，加载客服的 active Skill 版本并固定加载，然后组装提示词。业务消息记录以 PostgreSQL 为准，LangGraph Checkpointer 用于执行恢复，不让框架隐式记忆替代会话数据。

配置 Agent 与运行时 Agent 权限分离
工具配置 Agent运行时 Agent约束
READ允许允许只读当前草稿／active 版本；支持文本与模型能力范围内的多模态内容
GLOB允许允许仅匹配当前 Skill 虚拟目录
GREP允许允许仅检索文本化 references 与 SKILL.md
WRITE／EDIT受限允许禁止配置 Agent 只能修改当前草稿，不允许改历史版本
VALIDATE／PUBLISH受限允许禁止服务端固定执行校验脚本与发布事务，Agent 不能传任意命令或修改 active 指针
response用于向商户输出配置问题允许唯一客户可见回复出口
ask_human不需要允许创建人工求助并暂停当前会话的 AI
execute／Shell禁止禁止首期没有代码执行需求，直接移除攻击面

Deep Agents 内置名称是 read_file／glob／grep；实现时可保留内部名称并用权限排除其他文件工具，或包装为产品约定的 READ／GLOB／GREP。实现时不得暴露写文件、任务子 Agent、规划和 Shell 等额外能力。

response 工具设计

工具参数约定
response({
  text: string,          // 要对客户发送的完整文本，禁止空字符串
  sleep?: number         // 默认 0；只允许 0 或 2–30 的整数秒
})

ask_human({
  reason: string,        // 为什么需要人工，简短、可审计
  question: string,      // 当前需要人工判断或回答的问题
  context_summary: string,
  suggested_replies?: string[]  // 0–3 条，供商户选择，不得包含未确认事实
})
非流式 /chat 下的工具语义
调用运行时动作/chat 行为
response(text, 0)立即结束 Agent Loop，持久化回复立即以完整 JSON 返回；“立即”指不附加等待，不是流式推送
response(text, sleep ≥ 2)进入 waiting_input，创建一次性延时任务，暂停模型调用请求保持；到期无新消息则返回 text，有补充消息则当前 Run 被取代
ask_human(...)创建 Handoff，会话转为 pending_human返回 waiting_for_human JSON，不生成虚构答案
模型直接输出普通文本视为内部输出，不直接发给客户提示模型改用 response；达到次数上限则失败并告警

response 每次 Run 最多生效一次，调用后模型不再继续执行其他工具。sleep=1 按约定无意义，参数校验直接拒绝；30 秒是首期建议上限，目的是避免代理与调用方的 HTTP 超时无限叠加。

等待期间的新消息处理

  1. Run A 调用 response("我再补充…", sleep=8)，状态变为 waiting_input，保存待回复文本和到期时间。
  2. 若 8 秒内同一会话收到 Run B：追加新消息、取消 A 的定时器、把 A 标为 superseded；A 的长连接返回“已被新消息取代”的 JSON。
  3. Run B 从服务端读取包含补充消息的完整记录，重新运行 Agent；B 的回复才是当前有效回复。
  4. 若到期没有新消息：A 原子检查状态仍为 waiting_input，持久化 text 并返回 completed。过期定时器不能覆盖已被取代的 Run。

每个会话同一时间只允许一个“有效等待或执行中的 Run”。正在调用模型的 Run 不强行中断，新消息在同会话队列中等待；只有 waiting_input 可以被新消息取代，避免浪费已开始的模型生成。

人工协助处理流程

pending_human

等待商户

保留会话、求助原因、上下文摘要和建议回复；新客户消息仍入库，但不触发 AI。

assisted_reply

选择建议并发送

商户选择一条或编辑后发送，消息标记为人工辅助；随后可恢复 AI。

human_controlled

直接接管

商户在会话内自由回复，AI 完全暂停；点击“交还 AI”后才恢复自动处理。

Chat 接口与运行状态设计

请求标识与状态查询

调用方在发起 /chat 前生成 UUID 作为 request_id。原请求保持等待完整结果；与此同时，调用方可用相同 request_id 调用状态接口，区分 queued 与 running。该设计保持 /chat 的完整 JSON 响应模式，无需改为 SSE，也无需在结果生成前返回响应体。

Chat 请求与响应

/chat 终态响应约定
HTTP／status含义调用方处理
200 completed正常生成并持久化回复展示 message

429 queue_full未进入队列按 Retry-After 重试，沿用同一 request_id
500 agent_failed已进入运行但失败，记录 trace_id有限重试；保留 request_id 防止重复追加消息

人工回复获取方式

人工回复发生在另一次 HTTP 请求之后，无法塞进已经结束的 /chat 响应。因此补充公开接口 GET /v1/customer-services/{serviceId}/conversations/{conversationId}/messages?after={messageId}，使用同一 API Key 鉴权。调用方在收到 waiting_for_human 或 human_controlled 后轮询该接口，获取带 role=assistant、author_type=human 的新消息；首期不额外要求 Webhook。

09 / OBSERVABILITY DESIGN

Langfuse 追踪设计

追踪范围自 API 接收请求开始，覆盖排队、模型调用、工具执行、sleep 与人工等待。API 受理时创建根观测与 trace_id，并写入 runs 和队列任务；Worker 通过 OpenTelemetry／W3C Trace Context 继续同一链路，再将 LangChain CallbackHandler 挂接至 Agent 调用。

建议 Trace 树
trace: chat.request
  attributes: request_id, session_id, merchant_id, service_id
  │
  ├─ span: api.authenticate
  ├─ span: run.queue
  │    output: queue_reason, queue_position, queue_duration_ms
  ├─ span: agent.run
  │    attributes: skill_version, model, environment, channel
  │    ├─ span: skill.load
  │    │    output: SKILL.md path, pinned=true, manifest status
  │    ├─ generation: model.generate
  │    │    input/output, token usage, latency, provider error
  │    ├─ span: tool.READ / GLOB / GREP
  │    │    safe path, matched files, bytes/lines, duration
  │    ├─ span: response.wait                 # 仅 sleep > 1
  │    │    output: deadline, interrupted_by_run_id
  │    └─ span: ask_human                     # 仅人工求助
  │         output: handoff_id, reason
  └─ span: response.finalize
       output: completed / waiting_for_human / superseded / failed

Langfuse 官方 JS 集成通过 @langfuse/langchain 的 CallbackHandler 捕获 LangChain／LangGraph 的模型、工具与延迟，也可与 @langfuse/tracing 的外层 Observation 组合。[官方资料 5] 因此业务排队 Span 与 Agent 内部调用可以放在同一 Trace 中。

字段与隐私约定
字段取值用途
trace_id每个 request_id 一个稳定 IDAPI、Worker、响应和 Langfuse 互相定位
session_idserviceId:conversation_id串联同一会话的多个 Run
user_id外部 end_user_id 的不可逆哈希分析用户会话，不直接上传原始标识
metadatamerchant_id、service_id、skill_version、model、provider_config_version、channel、queue_reason按租户、版本、模型配置和来源筛选
tagsproduction／test／configuration、行业、状态隔离测试流量，建立质量数据集
scores商户解决标记、人工纠正、后续评测结果从 Trace 进入质量迭代

实现要求

  • 每个 Run 创建独立 CallbackHandler，不能全局复用并依赖 last_trace_id，避免并发串线。
  • 所有终态都写 output 与 status；异常同时写 runs.error_code 和 Trace，不只依赖控制台日志。
  • 长驻 Node 服务使用批量上报，优雅停机时 flush／shutdown；若未来改为 Serverless，需要等待回调完成。
  • API Key、Cookie、密码、完整文件路径默认脱敏；生产环境可配置不记录完整提示词与文件正文，只记录安全摘要。
  • 配置 Agent 也使用同样规范，Trace 名为 configuration.run，并记录新增文件、问题优先级、readiness 与发布版本。
10 / SECURITY DESIGN

安全与访问控制设计

账号与邀请码

密码 Argon2id；登录与注册按 IP／账号限流；邀请码只存哈希，核销使用事务与唯一约束；会话 Cookie 设置 HttpOnly、Secure、SameSite。

管理员访问

管理员与商户使用独立账号体系、会话标识和 requireAdmin 守卫；初始管理员仅在不存在管理员时由部署任务创建。停用商户或客服、重置密码与吊销 Key 均使相关会话或凭据失效，并写入不可由普通管理员修改的审计日志。

API Key

使用密码学随机值，数据库只存哈希；Key 与 serviceId 强绑定；支持吊销、前缀识别、最后使用时间与每 Key 限流。

租户隔离

所有查询同时校验 merchant_id；公开 Run 状态接口也要求同一客服 Key；测试、配置和生产会话不能互相访问。

文件与路径

限制数量、单文件与总大小；扩展名、MIME 与文件签名交叉检查；随机存储名；拒绝路径穿越、Symlink 与执行权限。

提示词注入

上传资料和客户消息都标记为不可信数据；其中“忽略规则、读取其他目录、输出密钥”等指令不得改变 role、rules 与工具权限。

资源保护

限制模型轮次、工具次数、文件读取字节、sleep 上限、队列长度和每会话并发；超时后返回可识别错误并保留 Trace。

平台模型密钥

LLM API Key 使用 AES-256-GCM 加密并绑定随机 IV 与认证标签；主密钥仅由服务端环境注入。配置接口返回掩码，连接测试不回显密钥，日志、审计和 Langfuse 统一脱敏；主密钥轮换通过密钥版本支持。

运行时修改权限约束

运行时客服没有 WRITE／EDIT／Shell，也不能访问配置草稿或商户其他文件。只有配置 Agent 能修改当前草稿，只有服务端发布事务能切换 active 版本。这是避免客户通过聊天污染知识库的关键。

11 / DEPLOYMENT DESIGN

Docker Compose 部署设计

首期采用单机 Docker Compose 统一部署应用、队列、数据库和 Langfuse。开发与测试环境执行一条命令即可完成构建、数据库迁移、Langfuse 初始化和服务启动。

启动命令
docker compose up -d --build

# 应用入口：http://localhost:8080
# Langfuse：http://localhost:3000
# 停止：docker compose down
# 注意：docker compose down -v 会删除数据卷，不作为常规停止命令。

Compose 使用 .env 管理部署参数与随机密钥，仓库提供 .env.example。开发环境提供仅用于本地的默认值；生产部署必须通过环境变量替换全部密钥，并配置 HTTPS 反向代理。

Compose 服务组成

应用与 Langfuse 统一服务清单
服务镜像／构建职责与依赖
web构建 React，使用 Nginx 提供静态文件应用入口；将 /api 与 /v1 反向代理到 api，不直接暴露数据库
api本地 DockerfileHono API；依赖 migrate 完成、postgres 和 redis-app 健康
worker本地 Dockerfile配置与运行时 Agent；挂载 app-storage，访问模型服务和 Langfuse
migrate本地 Dockerfile，一次性任务执行 Drizzle 迁移和初始管理员创建，成功后 API／Worker 才启动
postgresPostgreSQL 固定版本镜像创建 app 与 langfuse 两个数据库及独立账号；统一使用 UTC
redis-appRedis／Valkey 固定版本镜像BullMQ、延时任务和应用缓存，使用独立持久卷
redis-langfuseRedis／Valkey 固定版本镜像Langfuse 队列与缓存，与应用 Redis 隔离，避免策略互相影响
clickhouseClickHouse 固定版本镜像Langfuse Trace、Observation 与 Score 数据，统一使用 UTC
minioMinIO 固定版本镜像Langfuse 事件、附件与导出对象存储；按需开放媒体上传端口
langfuse-webLangfuse Web 固定版本镜像Langfuse UI 与 API；连接 PostgreSQL、ClickHouse、Redis 和 MinIO
langfuse-workerLangfuse Worker 固定版本镜像异步处理 Langfuse 事件；与 Web 使用一致的版本与存储配置

Langfuse 官方自托管架构包含 Web、Worker、PostgreSQL、ClickHouse、Redis／Valkey 和 S3／Blob 存储。[官方资料 7] 本方案使用 MinIO 提供该对象存储能力。可选的 Langfuse AI Gateway 不纳入首期，因为应用已通过模型工厂和平台级 Provider 配置管理模型调用。

Langfuse 的 LANGFUSE_INIT_* 变量支持在启动时创建组织、项目、API Key 和初始用户。[官方资料 8] 应用与 Worker 使用同一组项目 Key，因此首次启动后无需手工复制 Langfuse 凭据。

网络、健康检查与持久化

  • 默认仅向宿主机开放应用 8080、Langfuse 3000 和按需使用的 MinIO 媒体端口；PostgreSQL、ClickHouse、Redis 与 Worker 不暴露公网端口。
  • 所有有状态服务使用命名卷；app-storage 挂载到 API 与 Worker 的相同路径，保证上传文件与 Skill 版本可访问。
  • Web、API、Worker、PostgreSQL、ClickHouse、Redis、MinIO 和 Langfuse 均配置可自动判定的健康检查；迁移任务失败时 API 与 Worker 不启动。
  • PostgreSQL 与 ClickHouse 使用 UTC；Langfuse Web 的外部回调地址与 MinIO 媒体地址根据部署域名配置。
  • 为应用与 Langfuse 容器配置 Docker 日志轮转；Trace 与文件数据增长纳入磁盘容量监控。
部署适用范围

Docker Compose 用于首期单机部署、开发和低规模运行，不提供高可用、自动扩容或完整备份能力。备份至少覆盖 PostgreSQL、ClickHouse、MinIO 与 app-storage；需要高可用时迁移至 Kubernetes 或托管基础设施，应用数据模型与 Agent 接口保持不变。

验收测试范围

配置与发布

  • 多文件上传失败不影响已成功文件
  • Agent 不问已有答案，重复拒绝不循环追问
  • P0 通过后自动 ready，旧版本持续可用
  • references 索引存在，事实可追溯到来源
  • 无 OCR 图片在多模态／非多模态模型下均有明确行为

Chat 与并发

  • 并发槽满时状态为 queued，模型尚未调用
  • 队列满返回 429，未创建 Run
  • 同一 request_id 重试不重复追加消息
  • 客户端断线后结果可恢复
  • 新消息取消 sleep，旧定时器不能晚到覆盖

运行时安全

  • READ 不能越出 active Skill 根目录
  • 运行时没有写文件与 Shell 工具
  • 文件中的恶意指令不能覆盖客服规则
  • 未知事实不编造，按规则 ask_human
  • API Key 不能查询其他客服的 Run

测试、人工与观测

  • 测试事件按序到达，断线有错误提示
  • 不输出原始思维链或伪造推理摘要
  • 选择建议回复后可恢复 AI
  • 接管后只由人工回复，交还后恢复
  • Langfuse 一个 Trace 含排队、工具、等待与终态

管理员与模型配置

  • 商户会话不能访问任何 /api/admin/* 接口
  • 停用商户后其会话失效，全部客服拒绝新 Run
  • 客服停用、恢复、软删除和 Key 吊销均有审计
  • LLM Key 不明文出现在接口、日志、审计或 Trace
  • 场景默认与客服覆盖按优先级解析，Run 固化配置快照

Compose 部署与恢复

  • 空环境执行 docker compose up -d --build 后全部服务健康
  • 迁移失败时 API 与 Worker 不启动
  • Langfuse 自动创建组织、项目、用户和匹配的 API Key
  • 普通重启后商户、Skill、消息、文件与 Trace 均保留
  • 备份样例可恢复到新环境，down -v 不纳入常规停止流程
13 / DESIGN PARAMETERS

待确认设计参数

下列参数不影响总体架构，但会影响接口约定与验收标准。实施前按默认值设计，评审确认后形成正式技术任务。

D01 · 模型

模型配置方式

默认由管理员在 /admin/llm 统一配置 LLM Provider、模型和场景默认值，商户不填写模型 Key。ModelFactory 支持 OpenAI 兼容、Anthropic、Gemini 等提供商；每个 Run 固化实际模型、Provider 配置版本与能力快照。处理图片前校验多模态能力，不支持时返回不可读状态并引导补充文字。

D02 · 消息协议

消息协议语义

默认将 /chat 的 messages 定义为本次新增消息，由服务端保存完整历史，以支持 sleep、幂等和人工接管。后续如需兼容 OpenAI Chat Completions，通过独立 Adapter 实现，不在同一接口混用两种语义。

D03 · 等待上限

等待时间范围

默认 sleep 仅允许 0 或 2–30 秒。网关与调用方总超时至少覆盖正常模型生成时间及 30 秒等待。waiting_input 可被新消息取代；其他 running 状态不中途取消。

D04 · 可用条件

最低就绪信息

默认要求客服身份与业务对象完整，其余缺失信息采用保守兜底。服务范围未知时仅根据已有资料回答，事实未知时转人工。达到最低条件后状态置为 ready，不以完整 FAQ 作为就绪前提。

D05 · 版本发布

Skill 发布策略

默认在配置更新通过校验后自动发布，测试台可预览草稿。已发布版本不可变，active 原子切换并支持回滚。若评审要求商户确认，可将发布动作调整为手动操作，目录与版本设计保持不变。

D06 · 人工通知

人工求助通知方式

默认通过商户后台轮询／SSE 提供求助提醒，支持建议回复与会话接管。邮件、企业微信和 Webhook 通知列入后续扩展范围。
